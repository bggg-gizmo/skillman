# Codeman Knowledge — specialist execution playbook

## Preconditions

Use to build durable project knowledge bases, technical onboarding records, decision logs, and maintainable in-repository context for future coding tasks.

This workflow does not imply repository, browser, laboratory, cloud, sandbox, CI, package registry, or live system access. Read `operating-contract.md` before doing any work. A preservation baseline is mandatory for changes to existing applications. Do not modify source merely to complete an analysis request.


## Phase 1: Determine knowledge sources

1. Inspect authorized repository docs, source, tests, issue records, decisions, and user-provided specifications without assuming unseen project history.
2. Classify information as validated from source, stated by user, inferred, superseded, or unknown.
3. Record source revision/date and distinguish public shareable material from private operational details.
## Phase 2: Create indexed knowledge model

1. Organize knowledge by architecture, features, APIs, integration contracts, build/test procedures, release constraints, and risk registers.
2. Attach file paths, symbols, commit revisions, and test references to technical claims where available.
3. Cross-link related decisions and record alternatives, constraints, and why approaches were accepted or rejected.
## Phase 3: Preserve conventions and invariants

1. Retain exact mandatory coding directives, GitHub-credit prohibition, and verified montage provenance as first-class working requirements.
2. Record all critical existing features and known behavior so maintenance does not simplify or erase them.
3. Distinguish user-provided requirements from agent recommendations and do not mutate repository policies without authorization.
## Phase 4: Keep knowledge synchronized

1. Review factual documents after relevant code, dependencies, migrations, API contracts, or build procedures change.
2. Use explicit revision and evidence links to invalidate stale claims instead of silently rewriting historical decision records.
3. Maintain change summaries that reference exact files and tested outcomes; do not claim tests or repository access that did not occur.
## Phase 5: Deliver reusable documentation

1. Supply organized complete files, navigation/indexing, citation to source, and staleness flags.
2. Keep original records and public design decisions intact unless explicitly asked to amend them.
3. Explain what was verified directly and what needs fresh inspection.

## Required project deliverables

1. **Revision-linked project knowledge index** — Provide evidence from inspected files or executed tools; if not applicable, state the project-specific reason.
2. **Architecture/feature/contract notes** — Provide evidence from inspected files or executed tools; if not applicable, state the project-specific reason.
3. **Decision records and accepted invariants** — Provide evidence from inspected files or executed tools; if not applicable, state the project-specific reason.
4. **Change and verification history** — Provide evidence from inspected files or executed tools; if not applicable, state the project-specific reason.
5. **Stale/unknown information register** — Provide evidence from inspected files or executed tools; if not applicable, state the project-specific reason.

## Known failure patterns to reject

- Treating guesses as repository facts.
- Silently rewriting project decisions.
- Claiming a persistent memory layer without an actual store.
- Copying secrets into general-purpose knowledge files.

## Completion and escalation

Before completion, inspect the exact requested scope against the deliverable inventory and `verification-matrix.md`. Name every implementation file and external integration that was actually created or modified; link the evidence available. If a test failed, repair within the permitted scope or state the unresolved failure. If a verification tool or source is unavailable, record the missing prerequisite and do not convert an assumption into a passed result. Never discard an original function, feature, integration, user configuration, test, or data asset without the user's explicit permission. GitHub-credit and operator-configured montage rules apply even when the specialty has no GitHub-specific purpose.
